# 世界模擬遊戲（程式倉庫名稱：World-Library）

正在開發的「世界自主演化 → 神祇降臨 → 人物降臨」遊戲。正式遊戲預計使用 Godot（2D）＋ C#；世界模擬由純 .NET 8 程式庫 `WorldSimulation.Core`（模擬核心）負責，包括確定性亂數、排程等，不依賴 Godot。

## V0-06B｜遷徙人口建立新聚落（TEMP，待 GPT 審查）

缺糧聚落若在 TEMP 已知範圍（`KnownRouteMaxSteps` 格）內**每個可達聚落的消息都已傳到、而且沒有一個有糧**（或根本沒有可達聚落），就不再空等：一部分人（同 V0-06A 比例，帶等比例糧食與飢餓債）組成**開拓隊**，走向附近 TEMP `FoundingSearchMaxSteps`（示範值 3）格內「陸地、沒有聚落、不是別支開拓隊目的地、至少鄰接一格水域（TEMP 水源）」的最近空格（45F SETTLE_NEW／SETTLE_KNOW）。開拓隊同樣每週走 1 格、途中只吃自帶糧食；全數死於途中就是開拓失敗、不留下聚落（SETTLE_FAIL）。抵達時以倖存者建立**新聚落**：新的示範編號（只遞增、不重用）、記下建立週次與來源聚落、所在格依地形得到一個資源點；期初人口／糧食／飢餓債／資源點存量全部為 0，**人口、糧食、飢餓債全部由開拓隊帶入**（45G M1_SETTLE 新聚落不憑空，週結算發布前驗證）。每個聚落同時最多一支開拓隊在路上（TEMP）。不抽亂數；年度摘要多「新建聚落」數。

**怎麼看：** 開拓預設關閉（`FoundingEnabled`）。TEMP 測試情境 `DemoWeeklyTempConfig.FrontierSample`：開局聚落全部沒有糧食與再生（舊土地耗竭），新聚落的土地照常再生。文字介面：`--demo --seed 42 --years 100 --frontier`。CI 以 `WORLD_SIM_SETTLE_SMOKE=1` 在真 Godot 中重現：地圖上新聚落是**帶白圈的金色圓點**，歷史列表出現「建立新聚落「新聚落N號」：M 名遷徙者定居（…）」，點該格可看人口與來源聚落。

## V0-06A｜缺糧聚落人口沿相鄰格遷徙（TEMP，待 GPT 審查）

每週結算在「餓死」之後多一步**遷徙**（44B 順序 ⑧）：本週缺糧、倖存人數達 TEMP 門檻（`MinPopulationToEmigrate`，示範值 2）的聚落，若**已經傳到該聚落的消息**裡有「沒缺糧、沒飢餓債、仍有人」且 TEMP 陸路不超過 `KnownRouteMaxSteps`（示範值 6 格）的聚落，就有一部分人（`EmigrationShareDivisor`，示範值一半）帶著等比例的糧食與飢餓債組成**遷徙隊伍**出發，往路線最短的目的地走。出發當週停在來源格，之後**每週只走 1 格（相鄰六角格）**，途中只吃自己帶的糧食、照同樣規則挨餓或餓死（每筆途中死亡都有原因），抵達時人口、糧食、飢餓債一起併入目的地。第一週沒有任何消息，所以不會遷徙；沒有已知可達的有糧聚落就留下（45E MIG_NO_TARGET），不是人口自動平衡器。路線是 **TEMP 暫代**：六角格六鄰格相通、水域不可通行（起點終點例外），不是正式 `RouteSegment` 路網。不抽亂數。

**#61 補修（GPT 審查 #58 意見）：消息不是全知的。** 一個聚落的週報消息沿同一條 TEMP 陸路傳遞，每格要 TEMP `NewsDelayWeeksPerCell`（示範值 1）週：第 W 週、路程 d 格的來源只知道目的地第 W－d 週的週報，更新的消息還在路上；沒有陸路就沒有消息。每支隊伍記下它依據的消息週次（`NewsWeek`），外移事件會寫「依第 N 週傳來的消息前往…」。右側狀態欄也分成兩段：「聚落人口合計／遷徙途中人口／世界人口（各計一次）」是同一本人口帳；「V0-01 每日示範帳」是舊版獨立的 TEMP 帳（固定 5 人），與聚落人口無關。

人口帳改為「期初＋出生－死亡＋遷入－遷出＝期末」，糧食與飢餓債帳也加上隊伍帶入／帶出；每週另外檢查：每支隊伍只停在原格或走到相鄰格（45G `M1_MIG`）、來源遷出＝出發隊伍、目的地遷入＝抵達隊伍、**世界人口＝各聚落＋途中隊伍（只計一次）**只因死亡改變，任何一項不成立就在發布前拒絕。V0-05 年度摘要多了「遷出、遷入、年底途中」與外移／抵達事件數。

**怎麼看：** 示範種子 42 的一般設定很少缺糧；要看遷徙，用核心的 `DemoWeeklyTempConfig.LocalFamineSample`（只有示範聚落 #1 沒有糧食與資源）。CI 以環境變數 `WORLD_SIM_MIGRATION_SMOKE=1` 在真 Godot 中重現：地圖上的**紅色圓點**是途中隊伍（數字＝人數），歷史列表出現「某聚落 N 人因缺糧外移（…前往…）」，點隊伍所在格可看隊伍人數、方向與剩餘格數。新聚落建立留給 V0-06B。

## V0-05｜百年無畫面長測（TEMP，待 GPT 審查）

不開畫面，直接讓同一個示範世界跑 100 年，每年印一行摘要：

```bash
dotnet run --project src/WorldSimulation.ObserverCli -- --demo --seed 42 --years 100
```

每行是「第 N 年」的人口（出生、死亡）、有人聚落數、糧食（生產、消耗、缺糧）、資源存量、聚落事件數（飢餓、餓死、飢餓解除）與 V0-01 示範每日收穫合計；最後一行是「長測完成……守恆錯誤 0」。換種子（例如 `--seed 7`）可以比較不同世界的年度變化。長跑沿用 V0-04 的每週結算與原子提交：週帳不平衡會立即中止；每年結束時再用世界狀態的期初／期末值對帳一次（人口帳、糧食帳、資源存量帳、生產＝採收、死亡都有帶原因事件），有任何錯誤就列出並以結束碼 1 結束。自動測試用 3 個固定種子各跑 100 年，另跑一次 100 年饑荒情境，確認人口只會降到 0、不會被憑空救回。**「一年＝52 週＝364 日」是 TEMP 示範曆法**（正式曆法未定案），所有數值仍是 `TEMP`。

## V0-04A｜每週資源再生／生產／消耗＋資源帳與人口帳（TEMP）

每 7 個世界日，核心對每個 TEMP 聚落做一次週結算：**資源再生 → 勞動與生產 → 消耗**。資源點存量帳（期初＋再生－採收＝期末）、糧食帳（期初＋生產－消耗＝期末，生產必須等於採收：無魔法糧食）與人口帳（期初＋出生－死亡＝期末；出生、死亡要到 V0-04B 才有規則，目前固定 0）在發布前逐一檢查，不平衡就拒絕這次推進。每次推進一天都是一次原子提交：時鐘、排程、亂數、歷史、帳目與聚落存量先在私有副本上算好，最後一步才一起換上；自動測試會故意在提交中途丟出例外，確認世界狀態完全不變。週結算不抽亂數。

**怎麼看：** 開啟 Godot 專案按執行，按「下一天」到第 7 日（或按「快轉 30 天」），右側「本週帳目」會列出每個示範聚落的三本帳與「帳目平衡：是」。所有數值（初始存量、存量上限、各資源點每週再生量、每人每週產量與消耗、初始糧食）都在 `DemoWeeklyTempConfig` 並標示 `TEMP`，不是正式設定。缺糧只記數字，飢餓與死亡事件見下方 V0-04B。

**V0-04B 飢餓與餓死（TEMP）：** 每週消耗後，取得糧食低於需求的部分累積成「飢餓債」；每累積 TEMP 門檻（`HungerDebtPerStarvationDeath`，示範值每人 12）就有 1 人餓死，該部分飢餓債隨死者移除；只有在需求被實際糧食完全滿足的週，飢餓債才依 TEMP 速率（`HungerRecoveryPerPersonPerWeek`）下降。不抽亂數、沒有隱藏救濟。每筆飢餓、餓死、飢餓解除都是帶原因的事件，顯示在下方「結算歷史」；點聚落可看目前人口、糧食庫存與「飢餓狀態」。帳目另加「糧食來源：農牧＋採集」與「飢餓債」兩行。示範種子 42 的一般設定下聚落糧食充足；要看飢荒，可用核心的 `DemoWeeklyTempConfig.FamineSample`（CI 以環境變數 `WORLD_SIM_FAMINE_SMOKE=1` 在真 Godot 畫面重現）。門檻與速率都不是正式數值（正式公式在 39C，尚未定案）。

## V0-03B｜同一世界亂數登錄生成 TEMP 聚落／資源點／人口群體

`DemoObserverWorld` 只建立一個 `RngRegistry`：地形用 `GEOGRAPHY` 流，聚落數量與位置用 `ECOLOGY_INIT` 流，人口群體人數用 `POP` 流，每日收穫仍用 `RESOURCE` 流；地圖與聚落在建立世界時生成一次並快取。Godot 不再自行生成地圖，而是由 `ObserverRoot` 注入核心已生成的結果。打開 Godot 後，地圖上的金色圓點就是核心生成的 2～4 個 TEMP 聚落；點擊聚落所在格，右側會顯示聚落名稱、資源點（農地／林地／漁場，依該格地形）與人口群體人數。聚落數量範圍、人口群體人數範圍與聚落名稱都是 `DemoSitesTempConfig` 中標示 `TEMP` 的暫定值，不是正式設定。右側「人口」仍是 V0-01 糧食帳的示範人口，與人口群體人數尚未整合（留待 V0-04）。

## V0-03A｜核心生成六角地形與點格查詢（TEMP，待Claude獨立審查）

在既有Godot 4.7.2 .NET專案中，地形已改由純.NET8核心的 `DemoHexWorld.Generate(seed)` 使用既定 `RngStreams.Geography` **地理亂數流**逐格生成，Godot不再有獨立的地形雜湊產生器。每次以相同世界種子生成完全相同的96格內容；改變種子會改變部分格的地形。點擊任何示範六角格可在側欄查看**核心原始格子**的偏移／軸向座標和地形類別。

此模組明確位於 `WorldSimulation.Core.World.Demo`，欄位、座標映射和草原／森林／水域**都是TEMP實作選擇**；正式座標方向、地形子類、聚落、資源點、路網、人口尚未定案，不得把本畫面當作正式世界生成。金色圓點自 V0-03B 起改為核心生成的 TEMP 聚落。

自動測試除原Core功能外，會直接比較同種子／不同種子的**每格資料**，驗證每格地形從地理專用亂數流依序產生；Godot Headless會模擬點擊、核對側欄顯示Core原資料，並確認沒有 `TerrainCode` 等自行生成地形的函式。

**工程門檻：** 此項涉及Core資料與亂數，按照Notion03，**須先由Claude於Notion05明確獨立審查接受，才能合併至main**；CI全綠不等於已獲Claude批准。

## V0-02｜Godot 觀察者畫面（第一個真正圖形介面，TEMP 示範）

安裝 **Godot 4.7.2 .NET 版本**及 **.NET 8 SDK**；一般 Godot（沒有 .NET/C# 支援）無法編譯此遊戲。使用 Godot 編輯器選「匯入」，開啟 `godot/project.godot`，點選右上角 **建置（Build）**，接著按 **F6/執行目前場景** 或 **F5/執行專案**。

可在專案根目錄手動先確認 C# 有效：

```bash
dotnet restore godot/WorldSimulation.Godot.csproj
dotnet build godot/WorldSimulation.Godot.csproj --no-restore --configuration Release
```

**預期畫面：** 中央約12×8的彩色2D六角地圖（草地、森林、湖泊；金色圓點僅是示範聚落標記）；右側是世界日期、人口、食物存量、缺糧、抽樣次數及「下一天」「快轉30天」兩個按鈕；下方是該世界實際日結算所產生的事件歷史。畫面開啟時日期為第0日，不會自動流逝；按按鈕會從同一個 `DemoObserverWorld` 真正推進、更新食物與歷史。

**資料可信度界限：** 本畫面、地形、六角座標、示範聚落位置與人口/食物數字均為 `TEMP` 的視覺/數值Fixture，**沒有**載入正式Drive Excel、未產生正式HexCell、RouteSegment、Population或世界生成；六角格相鄰不代表已存在可通行路線。真 `WorldClock`／`Scheduler`／`RngResolutionDraft`／Demo 食物結算與歷史是同一Core執行邏輯；正式AtomicCommit/Save/History Kernel仍待後續階段。Godot C#僅依賴Core；Core不依賴Godot。

**驗收現況：** GitHub Actions除了以 `Godot.NET.Sdk/4.7.2` 編譯C#、執行核心245項測試和文字介面操作，**還會下載並以官方SHA-256校驗 Godot 4.7.2 .NET 引擎，在無畫面模式載入真正場景並觸發「下一天」「快轉30天」按鈕**，查核推進至第31天、產生31筆事件歷史；因而不只是編譯測試。但CI無畫面執行**不代表顏色、中文字型、版面縮放已由真人目視驗收**，仍建議用Godot .NET編輯器開啟場景實際查看。12×8六角格現採 **TEMP 奇數列偏移顯示**，形成近矩形錯列視覺；世界正式座標制度仍未定案。

## 立即試玩：第一個可執行切片（文字介面觀察者 v0）

請先安裝 [.NET 8 開發套件](https://dotnet.microsoft.com/download/dotnet/8.0)，在本程式倉庫的根目錄執行：

```bash
dotnet run --project src/WorldSimulation.ObserverCli -- --demo --seed 42
```

操作：`n` 推進一天；輸入 `1`～`1000` 快轉多天；`s` 查看人口與食物；`h` 查看事件歷史；`q` 離開。觀察與閱讀時，世界時間不會自行前進。

這個切片**真的執行世界排程**：使用世界時鐘（`WorldClock`）與排程器（`Scheduler`）推進時間，用隔離的亂數結算草稿（`RngResolutionDraft`）依種子確定性地試算每日資源收穫，進行食物生產、消耗、短缺的帳務，結算後增加一筆歷史。相同的種子、情境與輸入可以重現相同的事件與狀態。

**重要限制：這只是尚未平衡的示範情境**，不是完整的世界生成、人口生死、正式的 M1 經濟、Godot 正式世界地圖、存檔，也不是正式的跨系統原子提交。示範用的人口、食物與消耗數字只是本地示範資料，**不是** 設定檔 `01_世界參數` 的正式值，也不會寫入該表。此切片只示範「世界時間 → 事件 → 變化 → 可讀歷史」的第一條可執行路徑。
